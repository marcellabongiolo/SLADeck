# SLADeck Architecture

## 1. Product boundary

SLADeck is a multi-tenant request and SLA management SaaS. The initial version is intentionally scoped to one product workflow:

1. a user belongs to one or more organizations;
2. an organization has members with roles;
3. members create and manage requests;
4. requests have priority, status, assignee and an SLA policy;
5. the system calculates response/resolution deadlines;
6. workers create escalation/notification events as deadlines approach;
7. all important state changes are recorded in an audit log;
8. the dashboard displays operational workload and SLA health.

## 3. Core domain model

### User
Represents an authenticated person.

### Organization
Tenant boundary. Business data must always be scoped to an organization.

### Membership
Connects a user to an organization and stores their role.

### Request
Operational item being tracked.

Planned fields include:
- id
- organization_id
- title
- description
- status
- priority
- requester_id
- assignee_id
- sla_policy_id
- first_response_due_at
- resolution_due_at
- created_at
- updated_at
- resolved_at

### SLA Policy
Defines target durations by priority or policy.

### Comment
Team discussion attached to a request.

### Audit Event
Append-only record of important changes such as status, assignment, priority and SLA events.

### Notification
Represents an in-app/background notification generated by the system. SLA notifications are durable PostgreSQL records and are protected against duplicate creation by a request/stage/kind unique constraint.

## 4. Tenant isolation

Every business query must be constrained by `organization_id`.

A user being authenticated is not enough to access an organization. The authorization layer must verify active membership and sufficient role for the requested operation.

This invariant should be tested directly.

## 5. SLA engine

The SLA engine will be isolated from HTTP and persistence code.

Input:

```text
created_at + priority + SLA policy
```

Output:

```text
first-response deadline
resolution deadline
SLA state
```

Planned SLA states:

- healthy
- warning
- breached
- completed

Keeping this as domain logic makes it independently testable.

## 6. Background jobs

The API should not wait for scheduled SLA checks.

A worker will periodically:

- identify requests approaching a deadline;
- create escalation/notification events;
- avoid duplicate notifications through database idempotency;
- record the event in the immutable audit trail.

## 9. Security baseline

The MVP should include:

- password hashing;
- short-lived access tokens;
- refresh-token rotation or revocation strategy;
- tenant-scoped authorization;
- input validation;
- secrets only through environment variables;
- no credentials committed to Git;
- safe CORS configuration;
- tests for unauthorized and cross-tenant access.

## 10. Definition of complete

The portfolio MVP is complete when:

- the main workflow works end to end;
- database migrations are reproducible;
- authentication and tenant isolation are tested;
- SLA calculations and escalation jobs are tested;
- the frontend uses real backend data;
- Docker Compose starts the full stack;
- CI validates backend tests, frontend build and container builds;
- README claims only implemented capabilities.
